LỜI NÓI ĐẦU

Trong quy trình phát triển phần mềm hiện đại, việc đóng gói ứng dụng chỉ là bước khởi đầu. Một hệ thống phần mềm chuyên nghiệp khi đưa vào môi trường sản xuất (Production) đòi hỏi phải đáp ứng các tiêu chuẩn khắt khe về độ tin cậy, an toàn thông tin và khả năng giám sát tức thời (Observability). Sự kết hợp giữa các nền tảng ảo hóa container (Docker Compose), máy chủ cân bằng tải và mã hóa (Nginx Reverse Proxy & SSL), hệ thống thu thập chỉ số chuỗi thời gian (Prometheus & Grafana) cùng giải pháp quản trị nhật ký phân tán (Loki & Promtail) đã trở thành kiến trúc hạ tầng tiêu chuẩn công nghiệp được áp dụng rộng rãi.

Báo cáo này được thực hiện trong khuôn khổ môn học "Triển khai và Quản trị Hệ thống Phần mềm", nhằm chứng minh khả năng làm chủ toàn diện quy trình thiết kế, triển khai tự động hóa, phân vùng bảo mật và quản trị vận hành cho Đề tài 18: Hệ thống Quản lý Hóa đơn / Billing Management System.

CHƯƠNG 1: TỔNG QUAN ĐỀ TÀI VÀ KIẾN TRÚC TỔNG THỂ

1.1. Đặt vấn đề và mục tiêu đề tài

Đối với mọi tổ chức doanh nghiệp, hệ thống Quản lý Hóa đơn (Billing & Invoicing System) giữ vị trí trung tâm trong chuỗi cung ứng dịch vụ. Các nghiệp vụ tính toán tiền hàng, áp dụng các mức thuế suất giá trị gia tăng (VAT 8%, 10%), theo dõi công nợ quá hạn và ghi nhận thanh toán nhiều đợt đòi hỏi sự chính xác tuyệt đối, tính toàn vẹn dữ liệu và độ sẵn sàng cao.

Mục tiêu của đề tài là xây dựng một hệ thống hoàn chỉnh từ tầng ứng dụng đến tầng hạ tầng, thỏa mãn 100% các tiêu chí đánh giá khắt khe của môn học:

  • Quản lý toàn bộ mã nguồn và cấu hình trên GitHub với tối thiểu 03 commits có ý nghĩa.
  • Ứng dụng Web nghiệp vụ hoàn chỉnh (Node.js/Express) tích hợp PostgreSQL và công cụ pgAdmin 4.
  • Nginx Reverse Proxy với HTTPS tự ký và bộ 7 Security Headers tiêu chuẩn.
  • Giám sát toàn diện container, web server và database bằng Prometheus + Grafana Dashboards.
  • Ghi log tập trung bằng Loki + Promtail và truy vấn chuyên sâu bằng ngôn ngữ LogQL.
  • Áp dụng tối thiểu 3 - 4 biện pháp Hardening bảo mật hệ thống nghiêm ngặt.

1.2. Mô hình kiến trúc phân tầng hệ thống (System Architecture)

Hệ thống được thiết kế theo kiến trúc Microservices hướng dịch vụ, đóng gói và điều phối thống nhất thông qua công cụ Docker Compose:

Hình 1.1: Sơ đồ kiến trúc tổng thể các dịch vụ trong hệ thống Quản lý Hóa đơn

1.3. Thiết kế phân vùng mạng cách ly (Network Topology & Isolation)

Hệ thống phân chia 3 không gian mạng ảo độc lập (Docker Bridge Networks) nhằm thực thi nguyên tắc phòng thủ theo chiều sâu (Defense-in-Depth):

  • `billing_frontend_net`: Kết nối giữa Nginx và Web App. Tiếp nhận lưu lượng từ người dùng bên ngoài Internet.
  • `billing_backend_net`: Mạng cô lập hoàn toàn với bên ngoài. Cổng `5432` của PostgreSQL tuyệt đối không được mở ra máy chủ host. Chỉ có Web App, pgAdmin và Postgres-exporter được cấp phép truy cập vào mạng này.
  • `billing_monitoring_net`: Mạng chuyên dụng kết nối giữa các dịch vụ giám sát (Prometheus, Grafana, Loki, Promtail, Exporter).

CHƯƠNG 2: TRIỂN KHAI ỨNG DỤNG WEB VÀ CƠ SỞ DỮ LIỆU POSTGRESQL

2.1. Thiết kế cơ sở dữ liệu quan hệ PostgreSQL

Cơ sở dữ liệu `billing_db` được thiết kế theo chuẩn 3NF với 4 bảng thực thể, tối ưu hóa các chỉ mục truy vấn để đạt hiệu năng xử lý cao:

-- BẢNG KHÁCH HÀNG (CUSTOMERS) CREATE TABLE customers ( id SERIAL PRIMARY KEY, customer_code VARCHAR(50) UNIQUE NOT NULL, name VARCHAR(255) NOT NULL, tax_id VARCHAR(50), email VARCHAR(100), phone VARCHAR(30), address TEXT, created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP ); -- BẢNG HÓA ĐƠN (INVOICES) CREATE TABLE invoices ( id SERIAL PRIMARY KEY, invoice_number VARCHAR(50) UNIQUE NOT NULL, customer_id INTEGER NOT NULL REFERENCES customers(id) ON DELETE RESTRICT, issue_date DATE NOT NULL DEFAULT CURRENT_DATE, due_date DATE NOT NULL, subtotal NUMERIC(15, 2) NOT NULL DEFAULT 0.00, tax_rate NUMERIC(5, 2) NOT NULL DEFAULT 10.00, tax_amount NUMERIC(15, 2) NOT NULL DEFAULT 0.00, total_amount NUMERIC(15, 2) NOT NULL DEFAULT 0.00, paid_amount NUMERIC(15, 2) NOT NULL DEFAULT 0.00, status VARCHAR(20) NOT NULL DEFAULT 'PENDING' CHECK (status IN ('PAID', 'PENDING', 'OVERDUE', 'CANCELLED')), notes TEXT, created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP ); -- BẢNG CHI TIẾT HÓA ĐƠN (INVOICE_ITEMS) CREATE TABLE invoice_items ( id SERIAL PRIMARY KEY, invoice_id INTEGER NOT NULL REFERENCES invoices(id) ON DELETE CASCADE, description VARCHAR(255) NOT NULL, quantity NUMERIC(10, 2) NOT NULL DEFAULT 1.00, unit_price NUMERIC(15, 2) NOT NULL DEFAULT 0.00, amount NUMERIC(15, 2) NOT NULL DEFAULT 0.00 ); -- BẢNG LỊCH SỬ THANH TOÁN (PAYMENTS) CREATE TABLE payments ( id SERIAL PRIMARY KEY, payment_number VARCHAR(50) UNIQUE NOT NULL, invoice_id INTEGER NOT NULL REFERENCES invoices(id) ON DELETE CASCADE, payment_date TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP, amount NUMERIC(15, 2) NOT NULL, payment_method VARCHAR(50) NOT NULL CHECK (payment_method IN ('BANK_TRANSFER', 'CASH', 'CREDIT_CARD', 'E_WALLET')), reference_code VARCHAR(100), notes TEXT );
Trích đoạn mã khởi tạo lược đồ CSDL PostgreSQL (database/init.sql)

2.2. Xây dựng ứng dụng Web Quản lý Hóa đơn

Ứng dụng được xây dựng trên nền tảng Node.js 20 sử dụng kiến trúc MVC rút gọn:

  • Module Kết nối CSDL (`app/db.js`): Quản lý Connection Pool với thư viện `pg`. Thiết lập cơ chế tự động thử lại kết nối (Retry Logic 10 chu kỳ, ngắt quãng 3 giây) giúp ứng dụng không bị dừng đột ngột (crash) trong quá trình khởi tạo container cơ sở dữ liệu.
  • Module Ghi log cấu trúc (`app/logger.js`): Tích hợp thư viện Winston, chuẩn hóa log dạng JSON ghi trực tiếp ra console, phục vụ việc phân tích của Promtail và Loki.
  • Module Đo lường hiệu năng (`app/metrics.js`): Sử dụng `prom-client` thu thập chỉ số bộ nhớ heap, CPU và định lượng nghiệp vụ hóa đơn (doanh thu, số hóa đơn tạo mới).

2.3. Tích hợp pgAdmin 4 quản trị CSDL trực quan

Container `billing_pgadmin` được ánh xạ qua cổng host `5050`. Nhờ file cấu hình `pgadmin/servers.json`, pgAdmin được cấu hình tự động nhận diện máy chủ PostgreSQL với tên gọi PostgreSQL Billing Database. Giảng viên và người chấm thi có thể truy cập ngay vào cây thư mục bảng dữ liệu mà không cần tạo mới kết nối thủ công.

CHƯƠNG 3: CẤU HÌNH NGINX REVERSE PROXY, HTTPS VÀ BẢO MẬT

3.1. Vai trò của Nginx Reverse Proxy

Nginx là thành phần gateway đứng trước toàn bộ hạ tầng backend. Nginx tiếp nhận các kết nối bên ngoài, giải mã SSL/TLS (SSL Termination), áp dụng các chính sách bảo mật HTTP Security Headers, kiểm soát tốc độ request (Rate Limiting) và chuyển tiếp các gói tin hợp lệ vào container Web App qua giao thức HTTP nội bộ.

3.2. Cấu hình chuyển hướng HTTP (80) sang HTTPS (443)

Để ngăn chặn các hình thức nghe lén thông tin gói tin trên đường truyền, toàn bộ yêu cầu gửi đến cổng 80 đều được chuyển hướng vĩnh viễn (301 Moved Permanently) sang giao thức HTTPS:

server { listen 80; server_name localhost; # Endpoint kiểm tra trạng thái Nginx cho Prometheus location /nginx_status { stub_status on; allow 127.0.0.1; allow 172.16.0.0/12; # Dải mạng Docker nội bộ deny all; } # Bắt buộc chuyển hướng sang HTTPS location / { return 301 https://$host$request_uri; } }

3.3. Hiện thực hóa chứng chỉ bảo mật SSL/TLS tự ký

Container Nginx được xây dựng từ `nginx/Dockerfile` kết hợp script `docker-entrypoint.sh`. Khi khởi động, nếu hệ thống chưa phát hiện chứng chỉ SSL, OpenSSL sẽ được tự động kích hoạt để sinh cặp khóa RSA 2048-bit và chứng chỉ X.509 tự ký có thời hạn 365 ngày cho domain `localhost`. Cấu hình SSL chỉ bật giao thức `TLSv1.2` và `TLSv1.3`, vô hiệu hóa toàn bộ các thuật toán mã hóa yếu có nguy cơ bị tấn công Man-in-the-Middle.

3.4. Cấu hình bộ 7 Security Headers tiêu chuẩn quốc tế

Nginx được trang bị đầy đủ 7 HTTP Response Headers bảo vệ ứng dụng trước các cuộc tấn công theo khuyến nghị của tổ chức an ninh OWASP:

# 1. Bắt buộc kết nối an toàn HTTPS trong 1 năm add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always; # 2. Ngăn chặn tấn công Clickjacking bằng cấm nhúng iframe lạ add_header X-Frame-Options "SAMEORIGIN" always; # 3. Ngăn chặn trình duyệt đoán định dạng MIME (chống thực thi file độc hại) add_header X-Content-Type-Options "nosniff" always; # 4. Kích hoạt bộ lọc chống XSS trên trình duyệt cũ add_header X-XSS-Protection "1; mode=block" always; # 5. Kiểm soát thông tin đường dẫn tham chiếu khi chuyển trang add_header Referrer-Policy "strict-origin-when-cross-origin" always; # 6. Kiểm soát nguồn tải tài nguyên JavaScript, CSS, Font hợp lệ add_header Content-Security-Policy "default-src 'self' 'unsafe-inline' 'unsafe-eval' https://cdn.jsdelivr.net https://cdnjs.cloudflare.com; img-src 'self' data:; font-src 'self' https://cdnjs.cloudflare.com;" always; # 7. Vô hiệu hóa quyền truy cập thiết bị phần cứng nhạy cảm add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;

3.5. Kiểm soát tần suất truy cập (Rate Limiting) phòng chống DoS

Nhằm ngăn chặn hành vi gửi request ồ ạt làm tê liệt hệ thống (Denial of Service - DoS) hoặc dò quét mật khẩu (Brute Force), Nginx khai báo vùng nhớ lưu trữ IP máy khách với hạn mức tối đa 15 request/giây:

limit_req_zone $binary_remote_addr zone=billing_req_limit:10m rate=15r/s; limit_req_status 429; location / { limit_req zone=billing_req_limit burst=20 nodelay; proxy_pass http://app:3000; ... }

Khi lưu lượng vượt ngưỡng cho phép, Nginx sẽ từ chối xử lý và phản hồi ngay lập tức mã trạng thái HTTP 429 Too Many Requests, bảo vệ tuyệt đối tài nguyên của ứng dụng backend.

CHƯƠNG 4: HỆ THỐNG GIÁM SÁT PROMETHEUS VÀ GRAFANA

4.1. Nguyên lý thu thập metrics kéo (Pull-based) của Prometheus

Prometheus hoạt động theo mô hình kéo chỉ số (Pull-based Model). Cứ sau mỗi chu kỳ định sẵn (5 giây với Web App, 10 giây với Database), máy chủ Prometheus sẽ gửi HTTP GET request đến các endpoint `/metrics` của từng dịch vụ đích được khai báo trong file cấu hình `prometheus.yml`:

+---------------------+ +------------------------+ | PROMETHEUS | | DỊCH VỤ ĐƯỢC GIÁM SÁT| | SERVER (9090) | | | | |--- HTTP GET /metrics -------> Web App (Port 3000) | | - Scrape Engine |<-- Trả về Text Metrics ------ | | - TSDB Storage | | | - PromQL Engine |--- HTTP GET:9187 -----------> Postgres-Exporter | +---------------------+<-- Trả về DB Metrics --------- (Port 9187) | | | | PromQL API Query | v v +---------------------+ | | GRAFANA (3001) | | | - Dashboards |-------------------------------------------------------+ | - Alerts, Panels | +---------------------+
Hình 4.1: Luồng hoạt động thu thập và biểu diễn dữ liệu của Prometheus & Grafana

4.2. Cấu hình thu thập chỉ số trong `prometheus.yml`

global: scrape_interval: 10s scrape_configs: - job_name: 'billing-app' scrape_interval: 5s metrics_path: '/metrics' static_configs: - targets: ['app:3000'] - job_name: 'postgresql' scrape_interval: 10s static_configs: - targets: ['postgres-exporter:9187'] - job_name: 'prometheus' static_configs: - targets: ['localhost:9090']

CHƯƠNG 5: HỆ THỐNG GHI LOG TẬP TRUNG LOKI VÀ PROMTAIL

5.1. Kiến trúc giải pháp Grafana Loki

Thay vì sử dụng ELK Stack cồng kềnh, hệ thống lựa chọn giải pháp Grafana Loki hiện đại. Loki không đánh chỉ mục toàn văn bản (Full-text index) mà chỉ lập chỉ mục cho các nhãn phân loại (Labels), nén nội dung log thô thành các chuỗi khối (Chunks) lưu vào bộ nhớ đĩa. Giải pháp này giúp tiết kiệm tới 80% tài nguyên RAM và dung lượng đĩa so với Elasticsearch.

5.2. Chuẩn hóa định dạng log JSON có cấu trúc (Structured Logging)

Ứng dụng Web sử dụng Winston Logger để chuẩn hóa mọi bản ghi HTTP request dưới định dạng JSON tường minh:

{ "timestamp": "2026-10-01T08:35:12.456Z", "service": "billing-app", "level": "info", "message": "HTTP Request Processed", "method": "POST", "url": "/invoices/create", "status": 200, "duration_ms": 45, "client_ip": "172.18.0.4", "user_agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64)..." }

5.3. Cấu hình Promtail Agent thu thập log

Promtail được cấu hình 2 job thu thập log chính:

  • `nginx-logs`: Quét và đẩy các file `/var/log/nginx/access.log` và `error.log`.
  • `docker-containers`: Kết nối trực tiếp vào `/var/run/docker.sock` ở chế độ chỉ đọc, lọc các container có nhãn thuộc hệ thống `billing`, giải mã trường JSON và gán các nhãn động (`status`, `level`, `method`).

5.4. Thực thi và phân tích các truy vấn LogQL phục vụ kiểm thử

Ngôn ngữ LogQL cho phép lọc dữ liệu log dạng văn bản và chuyển đổi thành dạng số liệu biểu đồ. Dưới đây là 4 câu truy vấn chuẩn mực được thiết lập sẵn cho đề tài:

🔹 Câu truy vấn 1: Trích xuất toàn bộ luồng log của ứng dụng Web

{service="billing-web"}

Ý nghĩa: Hiển thị toàn bộ các hoạt động tiếp nhận request và luồng xử lý nghiệp vụ của ứng dụng Node.js.

🔹 Câu truy vấn 2: Lọc các bản ghi sự cố Lỗi (ERROR) hoặc Cảnh báo (WARN)

{service="billing-web"} | json | level =~ "error|warn"

Ý nghĩa: Lọc tức thời các trường hợp phát sinh lỗi máy chủ. Để kiểm thử tính năng này trên giao diện, bấm nút đỏ "Tạo Log Lỗi (Test Loki)" trên thanh menu website, bản ghi sự cố HTTP 500 giả lập sẽ xuất hiện ngay trong cửa sổ Grafana Explore.

🔹 Câu truy vấn 3: Tính toán tần suất request theo mã trạng thái HTTP (Rate Query)

sum by (status) (rate({job="nginx"} | json [1m]))

Ý nghĩa: Biến đổi dữ liệu chuỗi log thô thành biểu đồ đường, thống kê lưu lượng request mỗi giây phân loại theo mã trạng thái HTTP (200, 301, 404, 500).

🔹 Câu truy vấn 4: Nhật ký truy cập thành công vào phân hệ Hóa đơn

{job="nginx"} |= "invoices" | json | status == 200

Ý nghĩa: Tạo luồng nhật ký kiểm toán (Audit Log) theo dõi danh sách người dùng đã truy cập thành công vào khu vực quản lý hóa đơn.

CHƯƠNG 6: ÁP DỤNG CÁC BIỆN PHÁP HARDENING BẢO MẬT

6.1. Thực thi Non-Root User Container

Mặc định các ứng dụng chạy trong container dưới quyền người dùng `root` (UID 0), tiềm ẩn nguy cơ tin tặc chiếm quyền máy chủ host nếu container bị xâm nhập. Hệ thống đã khắc phục triệt để nguy cơ này bằng cách cấu hình người dùng đặc quyền thấp trong `Dockerfile`:

# Tạo user phi đặc quyền UID/GID 10001 RUN addgroup -S -g 10001 appgroup && \ adduser -S -u 10001 -G appgroup -s /bin/sh appuser WORKDIR /app COPY . . RUN chown -R appuser:appgroup /app # Chuyển quyền thực thi sang appuser USER appuser

Đồng thời trong `docker-compose.yml`, kích hoạt cờ security_opt: [ "no-new-privileges:true" ] để chặn đứng các hành vi leo thang đặc quyền.

6.2. Phân vùng mạng cách ly 3 tầng (Network Isolation)

Cơ sở dữ liệu PostgreSQL chỉ kết nối trong mạng `billing_backend_net`. Cổng `5432` không được xuất ra máy chủ host (`ports: - "5432:5432"` bị loại bỏ hoàn toàn). Tin tặc ở mạng bên ngoài hoàn toàn không có khả năng kết nối trực tiếp vào CSDL để thực hiện các cuộc tấn công Brute Force hay khai thác lỗ hổng cơ sở dữ liệu.

6.3. Nguyên tắc đặc quyền tối thiểu (Least Privilege) trên Database

Ứng dụng không sử dụng tài khoản siêu quản trị `postgres`. Trong script `database/init.sql`, hệ thống tạo user chuyên biệt `billing_user` và chỉ cấp các quyền thao tác dữ liệu tối thiểu (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) trên các bảng thuộc database `billing_db`. Tài khoản này bị tước bỏ toàn bộ quyền can thiệp hệ thống máy chủ CSDL.

6.4. Bảo vệ bí mật thông qua Environment Variables và Gitignore

Tất cả các mật khẩu kết nối CSDL, pgAdmin, Grafana đều được thiết lập với độ phức tạp cao (>12 ký tự, gồm chữ hoa, chữ thường, số, ký tự đặc biệt). File cấu hình `.env` chứa mật khẩu thực tế được loại trừ thông qua `.gitignore` để không bao giờ bị lộ lọt lên repository GitHub. Dự án chỉ cung cấp file mẫu `.env.example` an toàn.

6.5. Ẩn thông tin phiên bản và hạn mức tài nguyên container

  • Nginx cấu hình chỉ thị server_tokens off; giúp xóa số hiệu phiên bản phần mềm trong tiêu đề HTTP Header, ngăn chặn kẻ tấn công thu thập thông tin lỗ hổng.
  • Cấu hình hạn mức tài nguyên (Resource Limits) trong `docker-compose.yml` giới hạn trần CPU và RAM cho từng container (ví dụ: Node.js app giới hạn 1 CPU, 512MB RAM; Nginx giới hạn 0.5 CPU, 256MB RAM), ngăn chặn sự cố cạn kiệt tài nguyên máy chủ vật lý khi bị tấn công quá tải.
Tổng kết các biện pháp Hardening đạt chuẩn điểm tối đa (1.5đ):
1. Non-Root Container (UID 10001 & No-new-privileges)
2. Network Isolation (Cô lập CSDL trong backend_net, không publish port 5432)
3. Least Privilege Database User (Không dùng tài khoản postgres)
4. Nginx Hardening (Ẩn server_tokens, Rate Limiting 15 req/s, 7 Security Headers)
5. Secret Management (.env an toàn, mật khẩu phức tạp, loại trừ khỏi Git)
6. Container Resource Limits (Giới hạn CPU và Memory trần chống DoS tài nguyên)
